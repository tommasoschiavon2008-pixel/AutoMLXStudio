# Engineering command security model

Four distinct authorities are involved. (A) The agent may request only typed tools and allowed executable names; it cannot grant itself new authority. (B) “Allow Once” is a human decision for one exact mutation/command invocation, and “Deny” prevents that invocation from launching. (C) Selecting workspace W authorizes workspace file access only; it does not authorize unrelated user files. (D) Process execution is a separate capability: an approved command and all descendants must run under an OS-enforced filesystem policy, not merely start with cwd W.

Promised boundary: command processes may read and write the canonical authorized workspace; they may read essential OS and root-owned developer-toolchain files; they may read/write only their app-owned private runtime directory outside the workspace. They must not read sibling user files, arbitrary paths in the home directory, or outside symlink targets. Approval of `make target` does not widen that filesystem scope. All subprocesses inherit the process sandbox. The parent app remains unsandboxed for its existing model, persistence and local-network features; only Engineering command execution is sandboxed.

Known limitations: macOS Seatbelt profiles through `sandbox-exec` are available on this host but are deprecated/undocumented as a long-term third-party API. The implementation fails closed when the executable, trusted toolchain, or profile setup is unavailable; enforcement is validated by separate physical and automated probes, not an individual probe before every command. A future supported architecture would use a separate App-Sandboxed XPC/helper execution service, with per-workspace security-scoped bookmarks or explicit data passing, and full migration tests for local model, persistence, and LAN behavior. App Sandbox inheritance does not automatically pass dynamic PowerBox access to child tools; Apple's documentation specifically notes this. Build tools may depend on system SDK paths and private temporary files; these are explicit, narrow exceptions, not arbitrary user-data access. Group-based cancellation does not establish cleanup of a deliberately `setsid`-detached descendant, although that descendant remains subject to the inherited filesystem sandbox. This boundary does not claim defense against a compromised macOS kernel, malicious root-owned toolchain, or a user deliberately authorizing sensitive content *inside* W.

References: [Apple App Sandbox inheritance](https://developer.apple.com/library/archive/documentation/Miscellaneous/Reference/EntitlementKeyReference/Chapters/EnablingAppSandbox.html), [Apple App Sandbox protection](https://developer.apple.com/documentation/security/protecting-user-data-with-app-sandbox), [Apple Developer Forums on deprecated sandbox-exec](https://developer.apple.com/forums/thread/661939).
