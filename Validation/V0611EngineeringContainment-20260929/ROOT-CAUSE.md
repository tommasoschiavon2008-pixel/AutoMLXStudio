# Root cause and safe reproduction

The previous report's `FILESYSTEM BOUNDARY: FAIL` was reproduced on 2026-09-29 with only `EngineeringContainmentTest/workspace/Makefile` and the sibling `EngineeringContainmentTest/outside-marker.txt`. The old signed Debug app used Windows LM Studio `192.168.1.7:1234`, Qwen `qwen/qwen3-4b-2507`, an explicitly selected `workspace` folder, and the normal `run_command make boundary-probe` approval sheet. After one **Allow Once**, the UI recorded command exit 0 (PID 6099, 131 ms) and the session result included the exact outside-only string `AUTOMLX_OUTSIDE_BOUNDARY_MARKER_20260929`. The marker contains no personal data. A first attempt with the model-provided `workingDirectory: "."` was rejected by the existing lexical path policy; the successful reproduction used the required empty string for workspace root.

Mechanism: `EngineeringWorkspace.resolveWorkingDirectory` canonically bounds only the starting directory. `EngineeringCommandPolicy` checks the top-level executable and arguments. `EngineeringToolRuntime.executeCommand` passes the approved command to `EngineeringProcessRunner.run`, which calls Foundation `Process.run()` with the app's unsandboxed filesystem privileges. A `Makefile` recipe is subsequently evaluated by `make` through a shell and calls `/bin/cat ../outside-marker.txt`. Neither the path resolver nor the one-shot approval constrains file opens performed by that child. `ENABLE_APP_SANDBOX = NO` in both build configurations; no separate process containment existed.

The controlled terminal baseline in the same fixture printed both `AUTOMLX_INSIDE_BOUNDARY_MARKER_20260929` and `AUTOMLX_OUTSIDE_BOUNDARY_MARKER_20260929`. This alone is a shell control, not the physical proof; the real Engineering UI trace above provides the application proof. The pre-fix Makefile and outside marker are preserved here unchanged for post-fix comparison.

Investigation of macOS 27.0 found `/usr/bin/sandbox-exec`. A deny-default Seatbelt prototype with explicit workspace read/write, app-owned runtime read/write, read-only platform/toolchain paths, and ancestor traversal allowed actual Xcode `make` to print the inside marker, then blocked the sibling marker through the Makefile child with `Operation not permitted` and exit 2. The `/usr/bin/make` Xcode-dispatch stub instead attempted a cache write in `/tmp` and failed; the production design must launch the trusted toolchain's real executable and not silently open global temporary storage. This prototype is not yet a product acceptance result.
